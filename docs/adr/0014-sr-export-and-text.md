# ADR 0014: Structured Reports are written by Cornerstone's writer and mended by a pure step, and the measurements can be copied as text

Status: accepted (M11). Builds on [ADR 0004](0004-viewer-state-and-ordering.md) (one queue), [ADR 0005](0005-engine-runtime-lifecycle.md) (give back what the engine took), [ADR 0010](0010-shell-polish.md) (panel controls keep their `data-*` names), [ADR 0011](0011-config-layer.md) (config is data), and [ADR 0013](0013-structured-reports-and-pdf.md) (the report model, and reading a report). The plan is in [docs/specs/sr-export.md](../specs/sr-export.md), and what the spike found is in [docs/m11-spike.md](../m11-spike.md).

## Context

M10 reads a report and writes a PDF. A person who measures wants the numbers to leave the viewer in a form another system uses, and wants a text to paste into a report. A PDF is neither.

## Decision

- **The SR is written by Cornerstone's `MeasurementReport.generateReport`, in the engine, and then mended.** [engine/sr-write.ts](../../packages/core/src/engine/sr-write.ts) is the only code that calls the writer (the architecture rule). It builds the tool state from plain measurements, calls the writer, and writes the dataset to bytes with `dcmjs`. The writer is already in the engine chunk through the reader, so it adds no size. The port has one new method, `writeReport(input)`, which takes plain data (measurements in the order of the list, with the numbers the viewer holds, and the images they are on) and gives back bytes. No Cornerstone type reaches the public API.
- **What the writer makes is not shipped as it is.** [engine/sr-finish.ts](../../packages/core/src/engine/sr-finish.ts) is a pure function, with no Cornerstone import and its own tests, that mends what the spike found: the tracking unique identifier is random in the writer, so each is set from the measurement id (a 128-bit hash, `2.25.<number>`), and the same measurement has the same identifier in every export; the groups come out by image and by kind of shape, so they are put in the order of the list; the character set is missing, so `ISO_IR 192` is set; a probe has a placeholder `0`, which is replaced by the value in Hounsfield units, or left out when the viewer has none; the units of a region's statistics are Hounsfield units; a rectangle's minimum, which the writer leaves out, is added; the study is listed once as evidence; the equipment and the clock are honest (the clock is the one the registry gives); the SOP class is Comprehensive SR, as TID 1500 lists, in the dataset and in the file meta. A test checks every value against the length its DICOM field allows.
- **The shape goes beside its number**, as the standard puts it (an Image Region, and its image named Source). Cornerstone's writer puts it inside the number. highdicom's finder for planar measurements finds none in the writer's form and finds each one when the shape is moved. A bidirectional measurement has two shapes, so there is no one place for them: they stay inside their numbers, and the reader reads both forms. The cost is that OHIF and Cornerstone's own reader, which look inside the number, do not put these groups on the image. This was not tried in OHIF. The maintainer chose it.
- **The label is a short local code for the Finding and the whole label in a Comment.** Cornerstone's code, `CORNERSTONEFREETEXT`, has 19 characters in a field that holds 16, and a meaning is at most 64 characters, so a file with it is not valid DICOM and a long label is cut. The Finding has the code `LABEL` of the scheme `99DICOMVIEWER` and the first 64 characters, and the Comment has the whole label, in UTF-8. OHIF shows no label for it. The maintainer chose it. The reader takes a label from the Comment first.
- **The file has the patient's identity in it.** A DICOM object has to carry the patient's name, ID, and birth date, or a PACS will not file it. The writer copies them from the images, with the study's own IDs, whatever `showPatientInfo` says. This is unlike the PDF and the text. The menu item says "includes patient identity", and the guide says so. The file is made in the browser and nothing is sent.
- **The file is the report only.** It refers to the images by UID and has no pixel data.
- **`exportSr` goes through the queue**, gathers each image from the data source, and the engine registers the images nobody holds, claims them, writes, and releases them in a `finally`, as it does to read a report. A measurement on a series the source does not have makes the call reject and say how many, because a report must name the image. Each export is a new series and a new instance, with UIDs of the form `2.25.<random 128 bits>`.
- **The text is a second renderer of the report model.** [report/text.ts](../../packages/core/src/report/text.ts) writes one line for each measurement from the same model as the PDF, so they cannot disagree, and a test of the model covers both. The patient is left out unless `showPatientInfo`. Text is not limited to Latin-1. `exportText` shares the model, the title limit, and the rejections with `exportPdf`.
- **The Copy button and the Download menu.** Copy uses the clipboard, and when the browser refuses (a page that is not secure, no permission, no clipboard) the panel shows the text in a read-only box, selected, with a note, and never fails without saying. The Download menu has the items Text, PDF, and DICOM SR, follows the pattern of the toolbar menus (`aria-haspopup`, `menu` and `menuitem`, the arrow keys, Home and End, Escape from the button or an item, and the focus returns to the button), and uses only `--dv-*` tokens. The PDF item keeps the name `download-pdf` (ADR 0010). There are three new commands (`measurements.copyText`, `measurements.downloadText`, `measurements.downloadSr`).
- **What the panel offers is config.** `measurements: { downloadFormats, copyText }` (strict keys, the formats `text`, `pdf`, and `sr`, with no repeats). The default is everything. An empty list hides the menu. A format that is left out is left out of the panel only: the API and the commands still work, as with the other keys the config says what the shell shows and the API is the host's code. `viewer-config.schema.json` has the new key.
- **Reading a report puts right the text dcmjs reads wrongly.** dcmjs reads every text value one byte to a character whatever the character set, and the browser's "latin1" is Windows-1252. A report in UTF-8 (the viewer's, and most tools') showed `Ã©` for `é`, and a label in Chinese was lost. [engine/sr-items.ts](../../packages/core/src/engine/sr-items.ts) puts the text right, in place, for a file that says `ISO_IR 192`. This also mends M10.
- **The labels of the report controls are messages.** "Load report", "Download PDF", and what the panel says about a load were English only. They are in `ViewerMessages` with the new labels.

## Evidence

- **highdicom, a tool that is not ours, reads the file.** The `structured report` scenario of `pnpm matrix --only headless`, in both asset modes, loads the phantom's report, writes the SR twice, and has `tools/phantom/check_sr_export.py` read the first with highdicom (`srread`) and pydicom: the class, the template, the study and the patient of the images, one evidence entry whose images are in the study, a group for each measurement in the order of the list, each label, shape, image, number, and unit as the viewer holds them, no value over its field's length, no two groups with one identifier, and highdicom's planar measurement finder finding each one. The same identifiers in both exports and a new series in each are checked. The script has its own tests (`uv run pytest`), run against the report highdicom wrote.
- **The viewer reads it again.** The scenario serves the exported file to the mock DICOMweb server as a series of the study, loads it, and checks that the same measurements come back on the same images, with the same labels, to 0.01 mm. Unit tests do the same with the fake port, and with the real writer and reader for all six types.
- **The engine gives back what it took.** The count of images in use is the same after two exports as before.
- **The browser found two things the unit tests did not.** A rectangle had no minimum (the writer takes no minimum for a rectangle), and the Download menu did not close with Escape when it had been opened with the mouse, as the focus stays on the button.
- **Size.** The engine chunk is within its budget. See [m11-report.md](../m11-report.md) for the numbers.

## Consequences

- **A report that was exported and is loaded again has new ids**, from its own SOP instance, so the measurements it was made from are there twice unless they are cleared. The guide says so. Matching by tracking identifier is a later change.
- **OHIF does not draw these reports on the image**, and shows no label. Other tools that follow the standard find the measurements. No PACS has been tried, and nothing here shows that one accepts the file. `dciodvfy` (dicom3tools), which checks a file against the standard in full, has not been run.
- **An angle is written with Cornerstone's code, "Cobb angle"**, as the writer makes it, and as two lines. The viewer reads it, and another tool will call it a Cobb angle.
- **Single-frame images only**, as in M10.
- **There is no way to read a `.dcm` a person picks from disk.** `loadSr` takes the UID of a series of the study. A file comes back only through a data source that serves it.
- **The post-processing depends on what Cornerstone's writer makes** (its order of groups, its codes). It is pinned with the Cornerstone packages, and a test of every part fails when an upgrade changes it.
